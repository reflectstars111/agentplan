# ARD：面向长时程 AI 任务的可溯源与版本化状态运行时

**作者**: 俞乾齐

---

## 摘要

长时程 AI 任务要求系统在多轮交互中持续保存、追踪并一致地使用信息，而现有 LLM 应用通常缺乏系统化的状态管理。本文提出 ARD（Agent Runtime Database），一个面向 AI 任务的应用层运行时。ARD 提供三项机制：(1) **可溯源上下文组装**，通过六步管线（检索→过滤→排序→压缩→组装→预算）在上下文构造全过程中保留来源引用和信任级别；(2) **基于事件溯源的持久状态**，采用不可变追加日志和乐观并发控制；(3) **版本化状态查询**，以单调递增序列号支持时间点读取、审计追踪和状态恢复。

我们在 48 条单轮查询、10 个五轮交互场景以及并发与版本查询微基准上评估 ARD。受控组件递增实验显示，在混合检索到完整 ARD 的综合得分提升中，加入来源标识贡献了 +0.90，占总提升 +1.07 的 84%；引用准确性相应提高 1.27 分。信任级别和完整 MMU 带来有限的额外增益，而结构化 ContextPack 在减少 token 使用量的同时未独立改善质量。多轮实验中，持久状态使跨轮一致性代理指标平均提高 13.5%（t=2.58，p=0.030，d=0.82），但不同场景的效果从 +52% 到 -6% 不等。进一步的 2×2 试验提供了初步非劣效性证据：在当前任务、模型和上下文构造条件下，8K 上下文配合持久状态不劣于 32K 上下文的无状态配置（p=0.0045，δ=0.05）。结果表明，当前实现中最稳定的质量增益来自上下文来源的可追溯性，而非更复杂的过滤或预算策略。ARD 无需修改或微调底层 LLM，并以应用层机制提供持久化、冲突检测和版本审计能力。

## 一、引言

大语言模型（LLM）在广泛任务上展现出较强能力。然而，在**长时程任务**中，例如跨会话的项目开发、持续数天的论文分析和需求不断演化的系统设计，模型需要在多次交互中保存、追踪并一致地使用信息。仅依赖单次上下文输入，往往难以满足这一要求。

针对这一局限，当前常见策略是**增大上下文长度**。从 128K 到 2M tokens，更长的上下文窗口已成为重要发展方向。然而，扩大窗口主要增加单次调用可见的信息容量，并不能直接解决跨轮状态一致性、信息来源追踪和历史版本审计问题。基于这一观察，本文提出三个可检验假设：

**H1**：*显式持久状态能够提高需要跨轮信息累积任务的一致性，其收益随任务的状态依赖程度增加。* 本文不将状态管理视为所有长时程任务失败的唯一原因，而是考察一个更具体的问题：持久状态能否在特定场景中带来可测量的跨轮一致性收益？

**H2**：*将上下文窗口视为执行工作区并引入来源追踪，能够改善引用准确性和回答质量。* 常见的扁平拼接式 RAG 实现可能在组装上下文时弱化或丢失来源元数据。若在上下文构造过程中保留信息来源和信任级别，LLM 的回答将更易于验证和审计。

**H3**：*在本文的任务和上下文构造条件下，持久状态配合较小上下文窗口可以达到与更大无状态上下文相当的表现。* 若该假设成立，状态管理可作为单纯扩展上下文容量的一种补充路径。

为验证这些假设，我们提出 **ARD（Agent Runtime Database）**，将数据库系统中的事件溯源、乐观并发控制和版本化思想应用于 AI 运行时。ARD 不修改或微调底层 LLM，而是在应用层提供三项能力：

1. **可溯源上下文组装**：确定性六步管线（检索→过滤→排序→压缩→组装→预算）在上下文构造全过程中保留来源引用和信任级别，生成具有显式 token 预算的结构化 ContextPack。

2. **基于事件溯源的持久状态与乐观并发控制**：不可变追加日志（Event Store）作为状态的权威记录。状态变更通过 TransactionManager 执行：读取时记录键及版本号（`read_set`），提交时检查并发修改（`verify()`），发生冲突时放弃当前写入并按需重试，从而预防丢失更新。

3. **版本化状态与时间点查询**：每次状态变更获得单调递增的 `seq_num`，兼作版本号和事件序号。`StateStore.read(key, version=N)` 通过重放事件重建历史状态，`StateStore.history(key)` 返回完整版本链。TraceStore 记录控制循环的各个阶段，并与 Event Store 共享 `seq_num` 空间。

这些机制借鉴了成熟的数据库系统设计，包括元组版本化、日志恢复和乐观并发控制，并在 AI 运行时层面提供不可变事件、时序版本化和提交时冲突检测等语义。

本文的主要贡献：

- **来源追踪的受控证据**：组件递增实验表明，加入来源标识贡献了完整 ARD 相对混合检索总提升的 84%，是当前实现中最主要的质量增益来源。
- **持久状态的效果与边界**：在 10 个多轮场景中，持久状态显著提高跨轮一致性代理指标，但效果存在明显的场景异质性。
- **上下文与状态的初步比较**：小规模 2×2 试验显示，在当前实验条件下，8K 有状态配置不劣于 32K 无状态配置。
- **可复现的系统实现**：实现事件溯源、乐观并发控制、版本查询和审计追踪，并通过针对性测试验证其正确性与基本性能特征。

本文其余部分如下：第二章综述四组相关工作。第三章描述ARD架构和机制。第四章呈现实验结果。第五章讨论启示、局限和未来工作。第六章总结。

## 二、相关工作

我们的工作与四个研究领域相交：

**长期记忆与分层存储。** MemGPT（Packer et al., 2023）将 LLM 类比为操作系统内核，通过函数调用管理分层记忆。其后续系统 Letta 引入 Memory Blocks 和 sleeptime compute。LongMem（Wang et al., 2023）通过冻结骨干 LLM 和可训练 SideNet 实现编码与读取解耦。MemLong（Liu et al., 2024）则在单 GPU 上将可处理上下文扩展到 80K tokens。上述工作主要关注记忆容量与读取机制；ARD 进一步关注记忆来源、状态一致性和版本审计。

**上下文选择与预算控制。** RAPTOR（Sarthi et al., 2024）构建层次化摘要树以支持多尺度检索。HyDE（Gao et al., 2023）通过生成假设文档改进零样本稠密检索。Self-RAG（Asai et al., 2024）训练反思 token，以决定检索时机并评估生成质量。CRAG（Yan et al., 2024）在检索质量较低时触发补充检索。上述系统主要改进检索内容及检索时机；ARD 关注检索结果如何在保留来源信息的前提下被组装和预算化。

**Agent 状态持久化与可恢复执行。** 工作流系统（如 LangGraph、Temporal 和 Prefect）支持持久化执行与故障恢复，但其抽象重点通常是任务编排，而非面向 LLM 上下文的来源建模。Agent 检查点可以保存对话或执行状态，但不同系统在版本查询、细粒度恢复和并发冲突检测方面的支持程度不一。ARD 将这些能力统一到同一状态运行时中。

**数据库机制在 AI 系统中的应用。** 多版本并发控制、日志恢复和乐观并发控制已在数据库系统中得到广泛研究。ARD 并不提出新的数据库并发算法，而是将事件溯源、版本查询和冲突检测组合为面向 AI 运行时的应用级状态抽象。

现有工作通常分别研究记忆、检索或工作流持久化。ARD 将可溯源上下文组装、事件溯源持久状态和版本化审计追踪置于统一运行时中，使来源追踪、显式预算控制和版本化写回位于同一执行路径。

下表依据本文关注的五项能力进行定性比较；“部分”表示相关能力由模型策略或外围组件间接提供，而非系统级显式保证。

| 系统 | 确定性状态 | 预算控制 | 事务写回 | 版本化 | 源追踪 |
|---|---|---|---|---|---|
| MemGPT/Letta | 部分：LLM 自主管理 | 部分：LLM 控制 | 未显式提供 | 部分 | 部分 |
| LongMem | 部分 | 未显式提供 | 未显式提供 | 未显式提供 | 未显式提供 |
| RAPTOR | 部分 | 部分：隐式控制 | 未显式提供 | 未显式提供 | 部分 |
| Self-RAG | 部分：模型决策 | 部分 | 未显式提供 | 未显式提供 | 部分 |
| **ARD** | **显式提供** | **显式提供** | **显式提供** | **显式提供** | **显式提供** |

## 三、方法

### 3.1 系统架构

ARD 采用分层架构，并在逻辑上区分读路径和写路径：

```
API/CLI层
  ↓
Controller（Fetch→Plan→Load→Reason→Verify→Writeback）
  ↓
Context MMU（六步管线）
  ↓
Hybrid Retriever（向量+BM25+实体+结构）
  ↓
StateStore / KnowledgeStore / TraceStore
  ↓
TransactionManager（乐观并发控制）+ Event Store（不可变追加日志）
  ↓
SQLite / FAISS / BGE-M3
```

读路径：Context MMU→Retriever→Store 投影，直接查询当前投影视图。
写路径：Controller→Verifier→TransactionManager→Event Store→同步投影，提交完成后即可读取。

### 3.2 可溯源上下文组装

Context MMU 应用确定性六步管线。每条检索证据在整个管线中携带 `source_ref`（单个来源标识符）和 `trust_level`（`internal_memory`、`user_provided_data`、`external_untrusted`、`agent_generated`）。组装后的 ContextPack 使用 `source_refs` 保存来源标识符集合。

1. **RETRIEVE**：多策略混合检索，采用8因子评分公式：

```
Score = 0.35×语义相似度 + 0.20×关键词匹配 + 0.15×实体相关性
      + 0.10×新近度 + 0.10×重要性 + 0.10×结构相关性
      − 0.10×Token成本 − 0.20×信任惩罚
```

这些权重基于领域经验设定，并在实验中保持固定。本文未对其进行敏感性分析。

2. **FILTER**：按 `chunk_id` 去重，执行信任级别过滤并聚合来源引用。
3. **RANK**：基于优先级排序，保留得分最高的条目。
4. **COMPRESS**：根据 token 预算执行压缩，当前实现采用保留首尾信息的截断策略；RAPTOR 风格的聚类摘要作为可选扩展。
5. **ASSEMBLE**：构建 ContextPack，并按优先级排列各分节：系统指令（优先级 1）→当前查询（2）→工作记忆（3）→对话历史（4）→长期记忆（5）→检索证据（6）→工具结果（7）→输出预留（8）。
6. **BUDGET**：显式分配上下文预算：系统 10%、查询 5%、证据 35%、对话 10%、工作记忆 10%、长期记忆 10%、输出 10%，其余 10% 作为格式开销和安全余量。

与扁平拼接检索片段的实现相比，ARD 的 ContextPack 将 `source_refs` 作为一等字段保留，使 LLM 能够引用来源，也使 Verifier 可以检查生成声明与来源之间的一致性。

### 3.3 基于事件溯源的状态与乐观并发控制

**Event Store** 是不可变追加日志，也是状态的权威记录。每个 `StoreEvent` 均不可变，并携带以下字段：`event_id`（全局唯一）、`seq_num`（单调递增，兼作版本标识符）、`stream`（state/knowledge/trace）、`stream_key`（实体键，如 `agent:agent_001`）、`event_type`（created/updated/archived/deleted）、`payload`（变更内容）和 `txn_id`（所属事务）。

**TransactionManager** 实现乐观并发控制（Optimistic Concurrency Control，OCC）：

```
begin()      → 创建事务，记录到transactions表
add_event()  → 暂存写入事件到write_events缓冲区
record_read()→ 记录读取键及其当前seq_num到read_set
verify()     → 检查read_set中每个键的当前seq_num是否>read_at_seq
commit()     → 原子追加所有事件→同步投影→标记committed
rollback()   → 冲突时丢弃所有暂存事件
```

该机制用于预防**丢失更新**：当两个事务基于同一版本读取同一键时，先提交的事务成功，后提交事务的 `verify()` 检测到版本变化并拒绝提交。调用方可在重新读取最新版本后重试。ARD 面向以低冲突为主的 Agent 工作流，因此采用 OCC 以避免长期持有写锁。

### 3.4 版本化状态与可审计性

`seq_num` 作为版本标识符。`StateStore.read(key, version=N)` 通过重放截至 `seq_num=N` 的事件重建历史状态，`StateStore.history(key)` 返回完整版本链。TraceStore 记录控制循环的各个阶段（plan→retrieve→execute→verify→writeback），并与 Event Store 共享同一 `seq_num` 空间。

这些机制共同支持：(1) 时间点状态查询，(2) 决策链重建，(3) 恢复到先前版本，(4) 审计追踪。由于 Event Store 为追加式日志，“回滚”通过追加恢复或补偿事件实现，不会删除既有历史。

当前实现提供**事件溯源与乐观并发控制**语义，包括不可变事件、时序版本化和提交时冲突检测，但不构成完整的 MVCC 引擎。系统尚未实现显式快照时间戳、正式的版本可见性规则、非阻塞并发读写和隔离级别定义。

## 四、实验

### 4.1 实验设置

**知识库**：25 篇文档，覆盖 AI 系统、数据库系统和编程语言三个领域。
**嵌入模型**：BGE-M3（1024 维，本地 CPU 推理）。
**LLM**：DeepSeek Chat（temperature=0.3）。
**评估方法**：采用独立的 DeepSeek Chat 实例作为 LLM-as-Judge，在五个维度上进行 0–5 分评分：correctness（正确性）、completeness（完整性）、conciseness（简洁性）、citation_accuracy（引用准确性）和 groundedness（事实依据充分程度，分数越高表示生成内容越有依据）。综合分为五个维度的未加权均值。
**统计方法**：使用配对 t 检验、Bonferroni 多重比较校正、Cohen's d 效应量、Bootstrap 95% 置信区间和功效分析。下文中的样本量指参与配对比较的查询或场景数量。

**九种实验条件**：条件 3–7 共享相同的检索结果、排序、top-k 和生成提示，仅逐步加入来源元数据与上下文组装组件。

| # | 条件名 | 检索 | Source ID | Trust Level | ContextPack | MMU |
|---|---|---|---|---|---|---|
| 1 | bm25 | BM25 | ❌ | ❌ | ❌ | ❌ |
| 2 | vector | BGE-M3 | ❌ | ❌ | ❌ | ❌ |
| 3 | hybrid | BM25+Vec | ❌ | ❌ | ❌ | ❌ |
| 4 | hybrid_source_id | BM25+Vec | ✅ | ❌ | ❌ | ❌ |
| 5 | hybrid_provenance | BM25+Vec | ✅ | ✅ | ❌ | ❌ |
| 6 | ard_minimal | BM25+Vec | ✅ | ✅ | ✅ | ❌ |
| 7 | **ard_full** ★ | BM25+Vec | ✅ | ✅ | ✅ | ✅ |
| 8 | ard_no_filter | BM25+Vec | ✅ | ✅ | ✅ | 缺Filter |
| 9 | ard_no_budget | BM25+Vec | ✅ | ✅ | ✅ | 缺Budget |

**关键控制**：条件 3–7 的检索结果、排序、top-k 和生成提示保持一致，组件按照 Source ID→Trust Level→ContextPack→MMU 的顺序逐步加入。该设计减少了检索质量差异带来的混杂，用于支持组件层面的归因分析。

### 4.2 H2：来源信息组件递增实验（E1，n=48）

| 条件 | Tokens | 引用准确性 | 无幻觉 | 正确性 | **综合** |
|---|---|---|---|---|---|
| bm25 | 126 | 2.35 | 2.79 | 2.04 | 2.24 |
| vector | 400 | 2.44 | 2.83 | 2.62 | 2.54 |
| hybrid | 400 | 2.46 | 2.85 | 2.25 | 2.29 |
| hybrid_source_id | 474 | 3.73 | 4.27 | 2.79 | 3.19 |
| hybrid_provenance | 543 | 3.77 | 4.58 | 2.96 | **3.25** |
| ard_minimal | 422 | 3.79 | 4.46 | 2.73 | 3.10 |
| **ard_full** ★ | **422** | **3.71** | **4.54** | **3.04** | **3.36** |
| ard_no_filter | 422 | 4.06 | 4.67 | 2.81 | 3.24 |
| ard_no_budget | 422 | 3.81 | 4.38 | 2.79 | 3.15 |

**来源信息逐组件分解**（各比较均为 n=48）：

| 步骤 | Δ综合 | Δ引用 | 解读 |
|---|---|---|---|
| hybrid → hybrid_source_id | **+0.90 (+39%)** | +1.27 | 加入 Source ID 后出现主要增益 |
| hybrid_source_id → hybrid_provenance | +0.06 | +0.04 | Trust Level 在当前语料中的增益较小 |
| hybrid_provenance → ard_minimal | -0.15 | +0.02 | ContextPack 减少 token 使用，但未提高综合质量 |
| ard_minimal → ard_full | +0.26 | -0.08 | 完整 MMU 带来一定综合改善 |

**核心发现**：从 hybrid（2.29）到 ard_full（3.36）的综合得分共提高 1.07，其中加入 Source ID 后提高 0.90，约占总提升的 **84%**。Trust Level 仅带来小幅改善；结构化 ContextPack 的综合得分下降 0.15，但 token 数从 543 降至 422；完整 MMU 随后带来 0.26 的改善。在当前受控设置下，这一结果支持如下判断：**明确标注每条上下文的来源，是 ARD 质量增益的主要相关组件**。

在不启用完整 MMU 的配置中，hybrid_provenance 得分最高（3.25）；ard_full 的得分为 3.36，相对提高 3.5%。相较 hybrid 基线（2.29），ard_full 的综合得分提高 47%。需要注意，组件增量并非单调为正，因此该总增益不能简单解释为每个组件均独立有效。

**引用准确性**呈现最大的来源标注效应：hybrid_source_id 为 3.73，而 hybrid 为 2.46，差值为 +1.27。groundedness 也从 hybrid 的 2.85 提高到 hybrid_provenance 的 4.58。这一变化与“来源标识和可信度信息有助于模型依据证据生成”的解释一致，但当前实验尚不能完全区分来源语义、标签格式和提示结构各自的作用。

### 4.3 MMU 组件消融

ARD 内部比较（各比较均为 n=48，配对）：

| 比较 | Δ综合 | Cohen's d | p |
|---|---|---|---|
| ard_full vs ard_minimal | +0.26 | +0.32 | p<0.05 |
| ard_full vs ard_no_filter | +0.12 | +0.12 | ns |
| ard_full vs ard_no_budget | +0.21 | +0.20 | ns |

内部差异为小到中等（d=0.12–0.32）。其中，仅 ard_full 与 ard_minimal 的差异达到报告的显著性水平；移除 Filter 或 Budget 的比较均未达到显著水平。结合第 4.2 节的组件递增结果，来源标识对应的增益明显大于其余 MMU 组件，但仍需要随机 ID、错配 ID 等进一步对照来排除标签格式效应。

### 4.4 H1：持久状态及其适用边界（E2，n=10 个场景）

我们构造了 10 个多轮场景，每个场景包含 5 轮交互，并比较 No State（每轮独立执行 RAG+MMU）与 With State（通过 StateStore 持久化并加载先前轮次状态）两种配置。跨轮一致性采用三个信号组成的启发式代理指标：状态关键词召回（40%）、跨轮引用密度（30%）和回答连贯性（30%）。该指标反映状态延续程度，不等同于端到端任务正确率。

**总体结果**：No State 为 0.422（SD=0.084），With State 为 0.479（SD=0.094），差值为 +0.057（+13.5%）。配对 t 检验得到 t=2.58、p=0.030，Cohen's d=0.82。该差异在 α=0.05 水平上显著；在 n=10、d=0.82 的条件下，估计功效约为 0.65。

**分场景描述性结果**：

| 场景 | 类型 | No State | With State | Δ |
|---|---|---|---|---|
| 调试会话 | 分析型 | 0.280 | **0.425** | **+52%** |
| 论文深度分析 | 分析型 | 0.277 | **0.380** | **+37%** |
| 代码审查迭代 | 结构化 | 0.525 | **0.700** | **+33%** |
| 性能优化链 | 混合型 | 0.453 | 0.525 | +16% |
| 论文复现分析 | 结构化 | 0.427 | 0.477 | +12% |
| 项目开发 | 结构化 | 0.450 | 0.500 | +11% |
| API设计 | 结构化 | 0.480 | 0.525 | +9% |
| 数据库迁移规划 | 结构化 | 0.525 | 0.502 | -4% |
| 跨领域知识整合 | 分析型 | 0.425 | 0.400 | -6% |
| 设计演进与反转 | 结构化 | 0.375 | 0.352 | -6% |

整体而言，With State 在 7/10 个场景中表现更优，增益在调试会话（+52%）、论文深度分析（+37%）和代码审查迭代（+33%）中最大，另有三个场景出现小幅负面效应。由于每种场景仅有一个样本，这些分场景结果用于描述异质性，不能据此对任务类型差异作统计推断。

在本文定义的代理指标和场景集合上，结果支持 H1：持久状态提高了平均跨轮一致性，但收益并非在所有场景中稳定出现。

TransactionManager 在全部 50 轮 With State 交互中均成功提交，且未检测到冲突。由于该实验并未主动制造并发写入，这一结果仅说明状态写回流程正常运行；并发冲突检测由第 4.6 节的专项测试验证。

### 4.5 H3：状态与上下文长度的试验性比较（E3）

我们采用 2×2 设计比较 {8K, 32K} 上下文与 {No State, With State} 两个因素，每个单元包含 3 个场景。鉴于样本量较小，本实验被视为试验性分析。

| | 小上下文（8K） | 大上下文（32K） |
|---|---|---|
| **无状态** | 0.335 | 0.359 |
| **有状态** | **0.427** | 0.384 |

非劣效性比较关注 8K+State 与 32K+NoState。实验预先设定非劣效界值 δ=0.05；该界值依据 0–1 一致性指标的评分粒度选择。单侧检验得到 p=0.0045，在当前样本和界值下支持 8K+State 不劣于 32K+NoState。

State_8K 的点估计为 0.427，高于 NoState_32K 的 0.359，其 Bootstrap 置信区间满足预设非劣效标准。描述性差中差为 -0.067：State 在 8K 条件下的增益为 +0.092，在 32K 条件下为 +0.025。该模式提示状态管理可能在上下文受限时更有价值，但当前样本不足以稳健估计交互效应。

因此，在本文的任务、模型和上下文构造方式下，**8K 有状态配置达到了与 32K 无状态配置相当的表现**。该结论仅适用于当前试验设置，尚不能推导为状态管理普遍替代长上下文。

### 4.6 基础设施验证（T7，T8）

我们使用针对性微基准验证基础设施机制的正确性，并测量其基本性能特征：

**T7——OCC 并发性能**：9 种配置均通过数据完整性验证。吞吐量为 73–195 tx/s，并随并发度和冲突率变化。冲突率为 80% 时，吞吐量从 195 tx/s 降至 73 tx/s。4 个客户端、30% 冲突率配置下，p50 延迟为 11.7 ms，p99 延迟为 57.7 ms。每事务包含 5 个事件时，吞吐量降至 27.5 tx/s，表明事务大小是当前实现中的主要延迟因素。热点 key 分布在本测试规模下未显示明显影响。

**T8——版本查询性能**：当前状态读取为 0.009–0.020 ms，从 10 个事件增长到 10K 个事件时延迟增加约 2.2 倍。10K 个事件下，历史版本读取约为 1.5 ms，完整版本链查询约为 2.4 ms。投影重建是最耗时的操作，在 10K 个事件下约需 1.4 s。写入速率约为 145–200 个事件/秒。

**状态恢复正确性**：三版本恢复测试能够重建初始状态。在决策反转场景（REST→GraphQL→REST+auth）中，系统通过追加恢复事件保留最终架构选择，并选择性保留认证改进。

### 4.7 外部对比（E4，n=15）

我们在 15 条查询上比较 ard_full 与扁平上下文 RAG 基线。两者使用相同的检索结果、LLM 和知识库。ard_full 保留 `source_refs`、`trust_level` 并使用结构化 ContextPack；基线则将检索片段拼接为扁平文本提示。

| 系统 | 综合 | 引用 | 无幻觉 | Tokens |
|---|---|---|---|---|
| 扁平上下文 RAG | 2.73 | 2.67 | 2.67 | 385 |
| **ARD full** | **3.20** | **3.73** | **4.20** | 392 |
| Δ | **+0.47 (+17%)** | **+1.06 (+40%)** | **+1.53 (+57%)** | +7 |

在相同检索和模型条件下，ard_full 的综合得分提高 17%，其中 groundedness 的相对增幅最大（57%）。该结果在较小的外部比较集合上复现了第 4.2 节的变化方向，但由于样本量有限，且来源元数据与 ContextPack 结构同时变化，不能将差异完全归因于单一组件。与 MemGPT/Letta 等完整记忆系统的端到端比较留待后续工作。

## 五、讨论

### 5.1 来源标识是当前实现中的主要增益组件

本文最稳定的实验信号来自来源标识。第 4.2 节的组件递增实验显示，从 hybrid 到 hybrid_source_id 的综合得分提高 0.90，占 hybrid 到 ard_full 总提升的 84%。相比之下，Trust Level、ContextPack 和其余 MMU 步骤的净增益较小，且 ContextPack 的质量变化为负。

一种可能的解释是，扁平拼接检索片段会弱化证据与来源之间的对应关系，使模型难以生成可核验的引用。ARD 在整个管线中保留来源元数据，从而为生成和验证阶段提供更明确的证据边界。六步管线负责组织上下文，但在当前实验中，来源标识表现为更主要的增益组件。

引用准确性不仅是一项生成质量指标，也直接关系到系统的可审计性。明确的来源对应关系使用户和验证组件能够检查回答中的声明是否得到输入证据支持。不过，现有实验尚未区分真实来源语义、唯一标签以及格式化提示所产生的影响；随机 ID 和错配 ID 对照将有助于进一步识别机制。

### 5.2 状态管理的适用边界

总体实验表明，持久状态提高了跨轮一致性代理指标，但场景级结果存在异质性。调试、论文分析和代码审查场景的增益较大，而数据库迁移、跨领域整合和设计反转场景出现小幅下降。这说明状态并非越多越好：过期、冗余或与当前决策冲突的历史信息也可能增加生成负担。

从实践角度看，状态基础设施更适合优先部署在需要持续累积证据、约束或决策历史的工作流中；对于每轮均可由当前查询和知识库充分回答的任务，其收益可能有限。由于当前每类场景的样本量不足，本文将这一模式视为探索性发现，而非关于任务类型的确定结论。

当前 n=10 的总体差异达到统计显著（t=2.58，p=0.030，d=0.82），7/10 个场景呈现正向变化。按照观察到的效应量估计，将样本扩展至至少 14 个场景可使检验功效接近 0.8；更重要的是，后续实验应为每类任务设置多个独立场景，以检验场景异质性是否稳定。

### 5.3 上下文长度与状态质量

E3 的结果为状态与上下文长度之间的替代关系提供了初步证据：在当前实验条件下，8K+State 不劣于 32K+NoState（p=0.0045）。状态在 8K 条件下的描述性增益大于 32K 条件，但每个单元仅包含三个场景，尚不足以稳健估计交互效应。

因此，本文的结论限于**当前实验条件下的非劣效性**，并不意味着持久状态普遍优于长上下文。后续研究需要报告实际输入 token 数、截断比例和状态载荷，并在更多模型、任务和知识领域中复现该比较。

### 5.4 基础设施贡献与性能贡献

ARD 的 Event Store、TransactionManager 和版本化机制属于**基础设施贡献**。它们提供不可变记录、冲突检测、审计追踪和版本查询等系统级能力，但本文并未证明这些机制能够提高大规模 Agent 工作负载的吞吐或可靠性。T7/T8 仅验证了当前实现的正确性和基本性能特征；可扩展性优势仍需在真实并发工作负载中评估。

### 5.5 局限性

- **模型范围有限**：生成与评估均基于 DeepSeek Chat，结论尚未经过跨模型验证。
- **样本量较小**：E1 包含 48 条查询，但 E2 仅包含 10 个场景，E3 每个单元仅包含 3 个场景，尤其难以支持稳定的分类型和交互效应分析。
- **评估器偏差**：生成模型与 Judge 来自同一模型系列，可能存在模型偏好相关性；当前也缺少系统性人工评分与评分者间一致性分析。
- **代理指标限制**：E2 的一致性分数由三个启发式信号加权构成，反映状态延续程度，但不等同于任务正确性、用户满意度或端到端完成率。
- **非劣效界值敏感性**：δ=0.05 依据评分粒度设定，尚未报告不同界值下的敏感性分析。
- **并发规模有限**：T7 覆盖 1–8 个客户端和 0–80% 冲突率，但尚未覆盖多进程、分布式或 32 个以上客户端的场景。
- **语料范围有限**：知识库来自单一文档集合，跨领域泛化能力仍需验证。
- **经验参数未经调优**：八因子检索公式的权重由经验设定，尚未进行验证集调参或敏感性分析。
- **来源标识机制尚未完全分离**：当前实验没有随机 ID、错配 ID 或无语义占位符对照，因此不能完全排除标签格式和提示结构的影响。

### 5.6 未来工作

后续工作包括四个方向。第一，扩大多轮实验规模，并为每类任务构造多个独立场景，以验证状态收益的异质性。第二，引入人工双人评分、跨模型 Judge 和跨模型生成实验，报告评分相关性及评分者间一致性。第三，增加随机 ID、错配 ID 和 Trust Level 扰动实验，进一步分离来源语义、标签格式和上下文结构的作用。第四，在多进程、多 Agent 和分布式工作负载下评估 OCC、版本查询和投影重建的吞吐、可靠性与扩展性。

## 六、结论

本文提出 ARD，一个面向长时程 AI 任务的可溯源与版本化状态运行时，并围绕来源追踪、持久状态和上下文长度开展实验评估。主要结果如下：

1. **来源标识是当前实现中最主要的质量增益组件。** 在组件递增实验中，加入 Source ID 对应 +0.90 的综合得分提升，占 hybrid 到 ard_full 总提升的 84%；引用准确性提高 1.27 分。相比之下，其余 MMU 组件的净增益较小。

2. **持久状态提高了平均跨轮一致性，但效果存在场景差异。** 在 10 个五轮场景中，一致性代理指标平均提高 13.5%（t=2.58，p=0.030，d=0.82），场景级变化范围为 +52% 至 -6%。

3. **小规模试验支持状态与上下文容量之间存在一定替代关系。** 在预设非劣效界值下，8K+State 不劣于 32K+NoState（p=0.0045，δ=0.05），但该结果仍需在更大样本和更多模型上复现。

总体而言，实验提示：在当前设置下，明确保留每条上下文的来源，比进一步增加过滤、压缩或预算步骤产生了更稳定的质量收益。ARD 将这一机制与事件溯源、乐观并发控制和版本化状态结合，在不修改底层模型的前提下提供应用层状态保证。其质量收益的跨模型泛化以及基础设施机制在大规模并发 Agent 工作负载中的价值，仍有待进一步验证。
